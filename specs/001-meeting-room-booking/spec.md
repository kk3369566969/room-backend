# Feature Specification: 会议室预约后端

**Feature Branch**: `001-meeting-room-booking`

**Created**: 2026-11-15

**Status**: Draft

**Input**: User description: “依据会议室预定系统需求规格说明书，使用 Java 和 MySQL 实现后端，并产出后端说明文档与接口文档。”

## User Scenarios & Testing

### User Story 1 - 身份提交与审核 (Priority: P1)

学院教师和学生提交身份资料，负责人审核后获得对应业务权限；被拒绝的用户可以重新提交。

**Why this priority**: 未核验用户不能查询日程或预约，身份审核是所有业务流程的前置条件。

**Independent Test**: 使用虚构的学生、教师和负责人账号完成提交、通过、拒绝、重提，并验证权限只由服务端审核结果决定。

**Acceptance Scenarios**:

1. **Given** 用户尚未提交身份资料，**When** 提交姓名、学工号、师生类型和手机号，**Then** 系统创建待审核记录并返回审核状态。
2. **Given** 负责人处理待审核记录，**When** 通过学生或教师身份，**Then** 用户获得对应身份且可继续使用匹配的业务能力。
3. **Given** 身份审核被拒绝，**When** 用户查看结果并重新提交，**Then** 系统保留原审核历史并创建新的待审核记录。
4. **Given** 学工号已绑定其他有效账号，**When** 再次提交，**Then** 系统拒绝提交且不泄露已绑定账号信息。

---

### User Story 2 - 房间与日程查询 (Priority: P1)

已核验师生按日期查看五间会议室的资料、开放时段和占用情况，并只能看到他人的统一占用状态。

**Why this priority**: 查询是选择预约时段的基础，能够独立提供日程查询价值。

**Independent Test**: 以已核验账号查询房间列表和指定日期日程，验证开放时间、停用时间、占用时间和隐私字段展示正确。

**Acceptance Scenarios**:

1. **Given** 用户已核验，**When** 查询房间列表，**Then** 返回固定五间房间及容量、设备、资料状态，未知资料明确标记为待核实。
2. **Given** 房间存在待确认或预约成功记录，**When** 查询日程，**Then** 对其他用户显示统一已占用且不返回姓名、手机号、理由或审核内容。
3. **Given** 查询日期包含停用或非开放时段，**When** 查看日程，**Then** 分别显示停用和非开放状态，空闲时段才可作为预约候选。

---

### User Story 3 - 提交和取消预约 (Priority: P1)

已核验学生或教师提交单日单房间预约。学生提交后为待确认并立即占用时段，教师提交后直接预约成功；本人可在开始前取消。

**Why this priority**: 预约写入和冲突控制是系统核心业务，必须保证多个用户同时操作时不产生重叠有效记录。

**Independent Test**: 使用学生和教师账号分别提交合法、冲突、超容量、越界和重复请求，验证状态、占用和幂等结果。

**Acceptance Scenarios**:

1. **Given** 已核验学生选择开放且空闲时段，**When** 提交合法理由、人数、手机号和可选备注，**Then** 创建待确认记录并立即占用该时段。
2. **Given** 已核验教师选择开放且空闲时段，**When** 提交合法预约，**Then** 创建预约成功记录且不进入负责人待办。
3. **Given** 同一房间存在待确认或预约成功的重叠记录，**When** 提交新预约，**Then** 系统拒绝并说明冲突，不创建有效记录。
4. **Given** 预约人数超过已知容量或时间不在同日08:00—22:00，**When** 提交，**Then** 系统拒绝并返回可理解的校验原因。
5. **Given** 客户端因网络不确定而使用同一请求标识重试，**When** 服务端再次收到请求，**Then** 返回原处理结果且不重复登记。
6. **Given** 本人有待确认或预约成功记录且尚未开始，**When** 发起取消并确认，**Then** 记录转为已取消、释放时段并保留取消历史。

---

### User Story 4 - 负责人处理申请和资源停用 (Priority: P1)

负责人处理所有房间的学生申请，维护房间资料，创建或解除停用，并能追溯每次管理操作。

**Why this priority**: 学生申请无法闭环，且资源停用会影响多个预约，是运营和一致性的关键流程。

**Independent Test**: 以两个负责人并发处理同一申请，随后创建覆盖多个预约的停用，验证只有一次状态迁移、影响预览、统一取消、原因和通知完整。

**Acceptance Scenarios**:

1. **Given** 学生申请处于待确认，**When** 负责人确认且重新校验通过，**Then** 原记录转为预约成功并记录处理人，不生成第二份预约。
2. **Given** 学生申请处于待确认，**When** 负责人拒绝并填写原因，**Then** 记录转为已拒绝、释放时段并通知学生。
3. **Given** 两名负责人同时处理同一申请，**When** 两个操作到达服务端，**Then** 只有一个操作生效，另一个返回最新状态。
4. **Given** 负责人创建带原因的停用区间，**When** 预览并确认，**Then** 系统创建停用，取消所有重叠且尚未结束的待确认或预约成功记录，记录管理原因并通知受影响用户。
5. **Given** 已存在停用区间，**When** 负责人解除停用，**Then** 仅释放停用区间，不恢复已经取消的预约。

---

### User Story 5 - 结果通知与管理台账 (Priority: P2)

用户查看身份审核、预约处理、失效和停用取消通知；负责人按条件查询台账和操作日志。

**Why this priority**: 通知和可追溯记录保证用户知道结果，也满足负责人日常管理和问题排查需要。

**Independent Test**: 触发审核、确认、拒绝、失效、取消和完成等事件，验证相关通知、状态历史、管理筛选和隐私边界。

**Acceptance Scenarios**:

1. **Given** 业务状态发生需要告知用户的变化，**When** 系统完成状态迁移，**Then** 为相关用户生成站内通知且不依赖订阅消息授权。
2. **Given** 负责人查询管理台账，**When** 按房间、日期、状态或申请人筛选，**Then** 返回必要联系信息、预约详情和操作记录。
3. **Given** 预约到达开始时间仍未被确认，**When** 任何相关查询或状态处理发生，**Then** 记录可转为已失效并释放占用；到达结束时间的成功预约可转为已完成。

### Edge Cases

- 开始时间必须晚于服务端当前时间；客户端时钟不能绕过校验。
- 预约必须同日，开始时间小于结束时间，且在08:00—22:00内；相邻时段允许。
- 7060容量未知时仍要求人数必填，但不因容量未知拦截，提示向负责人确认。
- 负责人确认前容量或停用发生变化时，必须重新校验并返回失败原因。
- 取消、拒绝、失效、完成等终态不可恢复或编辑为有效状态。
- 修改或替换预约编号不能访问他人详情；未核验用户不能查询业务日程。
- 重复确认、重复取消、重复拒绝只返回当前状态，不产生第二次迁移。
- 负责人撤销资格时，未结束有效预约按管理取消处理并保留原因。

## Requirements

### Functional Requirements

- **FR-001**: 系统 MUST 支持用户提交姓名（1—50字）、学工号（1—30字符）、师生类型和中国大陆11位手机号，并校验必填字段。
- **FR-002**: 系统 MUST 以服务端审核结果确定用户是否为已核验学生或教师，管理权限必须单独授权，不能由请求参数伪造。
- **FR-003**: 系统 MUST 只允许已核验学院师生查询业务日程和提交预约。
- **FR-004**: 系统 MUST 提供7060、7081、7091、7119、7052五间房间的资料、开放时间和停用信息，未知容量或设备显示待核实。
- **FR-005**: 系统 MUST 按重叠条件“新开始＜已有结束且新结束＞已有开始”阻止同一房间的有效重叠预约；待确认与预约成功均占用。
- **FR-006**: 系统 MUST 校验预约为单房间、单日期、08:00≤开始＜结束≤22:00，开始时间晚于服务端当前时间，时间精确到分钟且不设置额外提前七天限制。
- **FR-007**: 系统 MUST 要求预约理由（1—200字）、预计人数（正整数）、手机号；备注可选且不超过500字；已知容量超限时拒绝。
- **FR-008**: 系统 MUST 为学生创建待确认记录，为教师创建预约成功记录；服务端不得接受客户端指定角色、状态、处理人或编号。
- **FR-009**: 系统 MUST 支持基于请求标识的幂等提交，并在并发提交、确认、取消时保证最多一个合法状态迁移。
- **FR-010**: 系统 MUST 支持负责人确认或拒绝任一房间的学生申请；拒绝必须有1—200字原因；确认时重新校验资格、容量、停用和冲突。
- **FR-011**: 系统 MUST 支持本人在开始前取消待确认或预约成功记录；开始后不得自助取消；原记录和原因必须保留。
- **FR-012**: 系统 MUST 支持负责人维护房间资料、创建或解除停用；创建停用必须先预览影响并在确认后统一处理受影响记录，原因必填。
- **FR-013**: 系统 MUST 生成身份审核、确认、拒绝、失效、取消和停用影响等站内通知，并支持查看和已读标记。
- **FR-014**: 系统 MUST 提供负责人按房间、日期、状态、申请人查询台账及关键操作日志；普通用户仅能查看本人详情和统一占用信息。
- **FR-015**: 系统 MUST 在处理查询和写入时识别已到开始但未确认的申请并释放占用，在结束后将成功预约标记为已完成。
- **FR-016**: 系统 MUST 使用北京时间作为服务端业务时间，并对所有未授权、未核验、越权和非法输入返回明确错误。

### Key Entities

- **用户**：微信关联标识、姓名、学工号、师生类型、手机号、身份状态和独立的管理授权。
- **身份审核记录**：用户身份快照、提交时间、负责人、结果、理由和处理时间。
- **会议室**：唯一房间号、地点、容量、设备描述和资料状态。
- **预约**：房间、申请人及身份联系快照、日期、起止时间、理由、人数、备注、状态、请求标识和处理历史。
- **停用安排**：房间、停用起止时间、原因、负责人、有效或已解除状态。
- **通知**：接收人、通知类型、关联业务、内容、生成时间和已读时间。
- **操作日志**：操作者、业务对象、动作、时间、结果和必要变更摘要。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 在100个账号、1万条历史记录和20并发持续5分钟的验收环境中，查询和提交接口P95不超过2秒，非预期错误率低于1%。
- **SC-002**: 并发提交、教师与学生竞争、确认与取消竞争各执行20次，任何时段最多保留一份有效占用记录。
- **SC-003**: 重复请求标识重试20次均返回同一业务结果，且不产生额外有效预约。
- **SC-004**: 至少5名首次使用代表用户中，4名无需指导在3分钟内完成查询和一次合法提交。
- **SC-005**: 未核验用户、学生、教师和负责人直接调用越权接口的验证用例全部返回拒绝，且不泄露他人个人信息。
- **SC-006**: 应用重启后成功预约、审核记录、通知和日志均可读取；一次恢复演练达到恢复点不超过24小时、恢复时间不超过2小时的目标。

## Assumptions

- 本期以人工身份审核作为身份资格基线，不接入学校统一身份认证，也不收集学校密码。
- 后端支持微信小程序 `wx.login` 凭证换取服务端会话；正式环境由部署方配置微信 `appid/secret`，本地开发保留可替换的 `X-User-Id` 适配器。
- 数据库使用用户提供的本机 MySQL `localhost:3306`、账号 `root`、密码 `1234`，连接参数允许通过环境变量覆盖。
- 首期只实现后端 REST API，不实现微信小程序界面、订阅消息和真实生产部署。
- 会议室设备、7060容量和特殊限制未知资料以“待核实”保存，负责人可补充。
- 课程验收使用虚构个人数据；数据保存期限和正式授权范围需上线前由学院确认。
